# FlexInfer External Research & Next-Step Guidance (2025-08-28)

This note validates FlexInfer’s design choices against Kubernetes best practices and adjacent projects, then outlines actionable next steps. Network access was constrained during this session; guidance is based on authoritative sources known as of 2024–2025 (Kubernetes docs, NVIDIA GPU Operator/NFD, Volcano, KServe/Seldon, Prometheus Go).

## Executive Summary
- Scheduler: Prefer Scheduler Framework plugins over extenders long term. Extenders work but are legacy and limit feature parity with upstream scheduling.
- GPU Discovery: Integrate with Node Feature Discovery (NFD) and NVIDIA GPU Operator labels/resources; avoid inventing overlapping label schema for presence/vendor.
- MIG/Resource Types: Support device plugin resources (e.g., `nvidia.com/gpu`, MIG resources) and use standard annotations/labels for accounting.
- Benchmark-Driven Scheduling: Viable; consider Volcano or keep custom scoring, but anchor on standard metrics (DCGM) and persisted perf data.
- Baseline Alternatives: KServe/Seldon rely on nodeSelectors/resources, not custom scheduling. Your operator adds differentiated value via perf-aware placement.
- Ops/Security: Harden RBAC, run as non-root, separate metrics mux/port, add NetworkPolicies and TLS options.

## Findings and Rationale

### 1) Scheduler Extender vs Scheduler Framework
- The Kubernetes project recommends using the Scheduler Framework for extensibility; extenders remain supported but have limitations (e.g., less integration with internal scoring stages, evolving API surface). Migrating to a framework plugin improves long-term supportability and performance.
- Interim: Keep the extender, but design your scoring/filter logic so it can be lifted into a framework plugin with minimal refactor (clear interfaces, pure functions, isolated cache).

Implication for FlexInfer:
- Keep current `/filter` and `/score` endpoints operational.
- Plan a feature flag to run as an in-tree/out-of-tree scheduler framework plugin later.

### 2) GPU Discovery & Labeling (NFD, GPU Operator)
- Node Feature Discovery (NFD) exposes standardized labels (e.g., `feature.node.kubernetes.io/…`) and detects vendor/pci features. NVIDIA GPU Operator integrates NFD and installs the NVIDIA device plugin and DCGM Exporter.
- Standard resource names are provided by device plugins (e.g., `nvidia.com/gpu`). MIG exposes `nvidia.com/mig-<profile>` resources; nodes may carry labels like `nvidia.com/mig.capable`.

Implication for FlexInfer:
- Use device plugin resources for scheduling guarantees, not only custom labels.
- Align basic discovery with NFD: treat FlexInfer labels as additive (arch, int4 capability, VRAM) while honoring NFD/GPU Operator signals for presence.
- Add compatibility with MIG: allow requesting `nvidia.com/mig-<profile>` and factor MIG profiles into benchmark matrix and scoring.

### 3) Benchmark-Driven Scheduling & Metrics Sources
- Benchmarking per model×device is valid; persistence in ConfigMaps works but consider versioning and TTL.
- For live utilization/cost signals, rely on:
  - DCGM metrics from GPU Operator for utilization/temperature/power.
  - Cloud/node annotations for cost (or external pricing feeds).

Implication for FlexInfer:
- Keep ConfigMap for durable TPS but add schema (model, quant, backend, device class, MIG profile, ts, version).
- Cache with TTL, and recompute on model or backend changes.
- For utilization, fetch DCGM metrics (or scrape Prometheus) rather than custom node annotations when available.

### 4) Alternatives: KServe, Seldon, Volcano
- KServe/Seldon primarily use standard k8s scheduling (nodeSelectors/tolerations/affinity). They don’t provide perf-aware cross-node scoring by default. Your extender/plugin is a differentiator.
- Volcano offers job scheduling, queueing, and custom plugins; can be leveraged if you evolve toward batch-style benchmarking or distributed inference jobs. For online inference, a custom framework plugin is typically sufficient.

Implication for FlexInfer:
- Continue operator-based lifecycle with a perf-aware scheduler component.
- Evaluate Volcano if you adopt batch benchmarking pipelines or complex multi-GPU gang scheduling.

### 5) Prometheus/Observability Practices (Go)
- Use a dedicated `http.ServeMux` and separate listener for metrics.
- Register Go/process metrics; consider pprof on a guarded endpoint.
- Provide health/readiness probes; add NetworkPolicies, TLS where needed.

Implication for FlexInfer:
- Update metrics exporter to use its own mux; avoid default global mux in libraries.
- Add Grafana dashboards for controller reconciliation, scheduler requests, TPS, DCGM utilization; add basic alerts.

## Actionable Next Steps

### A) Helm & Deployment (High Priority)
- Complete `charts/flexinfer/templates`:
  - Controller Deployment/Service/SA/Roles; CRD install hook or separate chart dependency
  - Agent DaemonSet with minimal RBAC, env `NODE_NAME` via Downward API
  - Scheduler Deployment/Service; config of weights via values; probes; NetworkPolicy
  - Benchmarker Job template referenced by controller
  - Optional dependency toggles for NFD/GPU Operator (document integration)

### B) Benchmarking (High Priority)
- Implement real backend integration for one target first (Ollama or vLLM):
  - Warmup, steady-state timed token generation; soft timeout
  - Persist `{model, backend, quant, deviceClass|migProfile, arch, vramGiB, batchSize, iterations, minDuration, tps, ts, version}`
  - TTL/refresh policy and re-benchmark triggers (image/model change)

### C) Scheduling Evolution (High/Medium)
- Abstract current filter/score into a library controllable by both the extender and a future framework plugin.
- Add MIG awareness; treat MIG profiles as distinct device classes; normalize TPS to per-partition capacity.
- Replace utilization annotations with DCGM metrics ingestion; fall back gracefully when unavailable.

### D) NFD/GPU Operator Alignment (Medium)
- If NFD present, trust `feature.node.kubernetes.io` for presence/vendor and merge FlexInfer-specific labels for arch/quant capability.
- Add a compatibility mode that disables FlexInfer’s “presence” label to avoid conflicts.

### E) Observability & Security (Medium)
- Metrics: dedicated mux, separate port, Go/process collectors, pprof (optional), standard `/healthz` and `/readyz`.
- Grafana: ship example dashboards.
- Security: non-root, read-only FS, drop caps, liveness/readiness probes, RBAC least-privilege, NetworkPolicies, image scanning.

### F) Testing & CI (Medium)
- Integration tests with envtest: reconcile -> benchmark Job -> ConfigMap -> Deployment/Service and endpoint population.
- Scheduler tests: filter & score logic with cached nodes, MIG, DCGM-based util.
- GitHub Actions: lint, unit, envtest, chart lint.

## Proposed Milestones
- M1 (2–3 weeks): Helm templates, basic real benchmarking for Ollama, integration tests, security hardening baseline.
- M2 (3–4 weeks): DCGM utilization integration, MIG-aware scheduling, dashboards/alerts, CI pipeline.
- M3 (4–6 weeks): Scheduler Framework plugin prototype; NFD alignment mode; cost modeling refinement.

## Notes on Backward Compatibility
- Maintain the extender path until the framework plugin is production-ready.
- CRD: add fields in a backward-compatible way (omitempty, defaults); version when changing semantics.
