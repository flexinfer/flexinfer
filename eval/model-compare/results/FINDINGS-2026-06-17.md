# Findings — gemma4-26b-a4b-gptq vs qwen35-moe-reasoning-5930k (2026-06-17)

First run of the `model-compare` harness against the two gfx1100 lanes, via the
flexinfer proxy. 28 objective items, deterministic scoring; perf = 3× streamed
200-token generations. Full data: `results/2026-06-17.md` (re-run `compare.py`
for the raw per-item JSON).

## Headline

| | gemma4-26b-a4b-gptq (7900xtx) | qwen35-moe-reasoning-5930k (5930k) |
|---|---|---|
| Accuracy | **100%** (28/28) | 96.4% (27/28) |
| Quality latency p50 | **0.12 s** | 3.72 s |
| Decode tok/s p50 | 72.3 | 34.5 |
| TTFT p50 | 0.10 s | 0.27 s |

**On this objective set, gemma4 is the better pick: equally/at-least-as accurate,
and ~30× lower latency per answer.** That is the expected result and an honest
one — the set is deliberately *easy and objective*, which is the regime where a
fast non-reasoning model shines and a reasoning model's "thinking" is pure
overhead. It does **not** probe the hard multi-step problems where qwen35's
reasoning would be expected to win; a harder benchmark (competition math,
multi-constraint logic, long proofs) would likely flip the quality column.

## What the data shows

- **Both are highly capable on basics.** Arithmetic, factual, code, instruction-
  following, and word-problem reasoning were 100% for both. qwen35 even nails the
  classic trap items gemma4 also gets (bat-and-ball → 5; "100 machines" → 5).
- **qwen35 over-reasons on trivial questions.** It spends hundreds–thousands of
  *reasoning* tokens before answering even "what is the capital of Japan" (469
  reasoning tokens for "Tokyo") or "how many continents" (1,407 reasoning tokens
  for "7"). That is why its per-answer latency is ~30× gemma4's despite a similar
  raw token rate.
- **qwen35's only miss is a self-inflicted budget timeout.** `logic-1` (a simple
  syllogism) ran 3,327 reasoning tokens, blew through the 1,024-token output cap,
  and emitted garbage (`- All r!!!!!!!!!`) instead of "yes". This is a real
  failure mode for a reasoning model under a fixed output budget — not a
  knowledge gap. A larger `--max-tokens` would likely recover it (at even higher
  latency).
- **gemma4 answers tersely** (2–6 completion tokens/item) and instantly
  (~0.1 s) — ideal for the daily-driver/agent-tool role it serves.

## Caveats on the numbers

- **As-deployed, through the proxy, client co-located on the qwen35 pod.** Both
  models hit the same `flexinfer-proxy` path under identical conditions, so the
  *relative* comparison is sound, but absolute tok/s differ from isolated
  single-stream benchmarks (qwen35 measured ~79 tok/s on localhost vs 34.5 here —
  proxy hop + the bench client sharing the serving pod's CPU).
- **gemma4's 72.3 tok/s is spec-decoding-inflated** (it runs n-gram SD; accepted
  draft tokens arrive in bursts). It is not directly comparable to qwen35's
  34.5 tok/s (no SD). For a like-for-like decode-kernel number, see the isolated
  graph-mode benchmark (qwen35 ~79 tok/s single-stream) in
  `deploy/debug/qwen36-currency-canary-model.yaml`.
- **Easy set, deterministic scoring.** The substring/exact checks are robust to
  qwen35's verbosity (it explains; we score the embedded final answer), but the
  difficulty ceiling is low. To differentiate *capability*, add harder items.

## Recommended next steps

1. Add a **hard reasoning tier** (GSM-hard / multi-step logic / constraint
   puzzles) so the eval can show where qwen35's reasoning pays off — that is the
   comparison that justifies keeping a slower reasoning lane.
2. Route by task: keep gemma4 as the default fast lane; send genuinely hard
   reasoning prompts to `qwen35-reasoning`. (A budget guard for the reasoning
   lane would avoid the `logic-1`-style empty-answer timeouts.)
3. Wire this harness into the weekly `deploy/tasks/model-eval-gauntlet` so the
   quality+latency comparison is tracked over time, not just throughput.
