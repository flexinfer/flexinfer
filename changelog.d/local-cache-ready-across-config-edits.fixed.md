A config-only edit no longer reloads a runtime-served lane that uses a staged `strategy: Local` `HF://` cache. The cache was ready only for the generation it was staged at, so any spec edit re-ran the `<model>-cache-stage` Job and held the cache not-ready until the Job exited "already cached". On 2026-10-25 the Flux apply of !1153, which only removed `flashAttention: false` from `deploy/models`, did this on every radeonvii lane. For about 8 s they failed runtime eligibility ("staged Local cache is not ready"), fell back to the Deployment path (throwaway `bge-large-radeonvii` and `gte-qwen2-1p5b-radeonvii` Deployments, Service selectors restored then cleared again), and the gfx906 runtime restarted the gte-qwen2, bge-reranker and orpheus subprocesses with a 5–7 s gap each. The CPU router `qwen3-1p7b-tools-radeonvii` rolled once.

`status.cache.stagedKey` (new) records a digest of what the stage put on disk and where: `spec.source`, the resolved download options (`ggufFile`, relative `mmproj`, `hfAllowPatterns`, `hfIgnorePatterns`, `hfRevision`), `vaeRepo`, the cache directory and `spec.nodeSelector`. A ready cache whose recorded key matches the current spec stays ready across the generation bump and starts no Job. Any change to those inputs, including a move to another node or `cache.hostPath`, stages again as before.

The Models CRD gains the optional `status.cache.stagedKey` field (the HelmRelease applies CRDs with `CreateReplace`). Statuses written before it fall back to the generation check, and the controller records the key on its first pass over each ready cache: one status write per staged Local HF Model on roll-out, no stage Jobs.
