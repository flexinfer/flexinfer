llama.cpp `spec.config.flashAttention: false` now passes `--flash-attn off`. Before, the backend rendered only `true` (`--flash-attn on`) and dropped `false`, so llama.cpp's default `--flash-attn auto` (every pinned build from b8173 on, plus `rocm-gfx906-patched-v3`) turned FA on wherever the device supports it, gfx906 and CPU included. Every lane that said `false` has been running on `auto`, which logged `Flash Attention enabled` on both gfx906 lanes measured. Unset still renders no flag and keeps `auto`. The controller now rejects `flashAttention: false` next to a quantized `cacheTypeV`, because llama.cpp refuses that context; the Model goes `Schedulable=False` instead of crash-looping at load. An A/B on the live `gte-qwen2-1p5b-radeonvii` command line (row `gfx906-llamacpp-flash-attn-ab-2026-10-24` in `.loom/60-validation-matrix.md`) showed FA off saves no VRAM (compute buffer 302 vs 303 MiB; +10 MiB at ub 1024 on the Qwen3 reranker), runs 3–16 % slower, and moves embeddings by up to cosine 0.99963. The 12 `deploy/models` lanes that carried the never-effective `false` therefore drop it and stay on `auto`, the setting they were qualified on, so the controller and runtime rolls change none of their arguments. Without this, the Weaver router (`qwen3-1p7b-tools-radeonvii`, `cacheTypeV: q4_0`) would have failed to load. The embeddinggemma-2 qualifier now leaves the key unset too. Takes effect for runtime-managed lanes at the next gfx906 / gfx1100 runtime image roll, and for dedicated Deployments at the next controller roll.
